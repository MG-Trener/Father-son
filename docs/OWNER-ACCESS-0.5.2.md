# 0.5.2 / 19 — доступ владельца

Статус: production-миграция применена 7 октября 2026 после отдельного подтверждения владельца. Проверено сохранение трёх существующих сеансов и блокирование неподтверждённого входа через RLS и RPC. [Релиз 0.5.2/19](https://github.com/MG-Trener/Father-son-releases/releases/tag/android-v19) опубликован, каталог обновлений проверен через публичный HTTP RPC приложения.

## Выполненное восстановление

7 октября 2026 по прямому поручению владельца сброшена ошибочная регистрация второго пользователя: удалены refresh tokens, сеансы, Auth user и его отдельная ошибочная семья по проверенным связям FK. Перед удалением проверены отсутствие других участников и объектов Storage. После удаления проверены отсутствие ошибочного аккаунта/семьи и сохранность исходной роли папы. Адреса и идентификаторы пользователей в репозиторий не сохраняются.

## Подготовленные изменения

- Приложение предназначено для одной существующей семейной команды. Роль папы закрепляется за единственным текущим родителем в закрытой таблице `private.app_owner`; адрес берётся из Auth, пользовательские metadata не используются.
- Существующие сеансы владельца сохраняются в закрытом списке. Новый сеанс с паролем не получает доступ к семейным данным до подтверждения почтой. Проверяются реальная запись `auth.sessions`, срок и серверная запись способа входа `auth.mfa_amr_claims`, а не клиентское утверждение об одобрении.
- Одноразовая ссылка Supabase возвращает пользователя в `papaiya://auth-callback`. Точный redirect добавлен в настройки Auth. Стандартный бесплатный шаблон содержит ссылку; платный SMTP для этого не подключался. Приложение просит открыть письмо на новом телефоне. Доставка конкретного письма и Android-переход требуют проверки владельцем.
- Исправление после проверки на телефоне сына: основной Auth `Site URL` тоже установлен в `papaiya://auth-callback`. Ранее он оставался `http://localhost:3000`, поэтому регистрация без явного `emailRedirectTo` подтверждала почту, но открывала неработающий адрес. Настройка исправлена на сервере и сохранена в `supabase/config.toml`; установленный APK 0.5.2 уже поддерживает callback, новый APK для этого исправления не требуется. Уже подтверждённому пользователю достаточно вернуться в приложение и войти с паролем; старое письмо повторно использовать не нужно. Основание: [Supabase Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls).
- Серверная проверка встроена в существующий предикат семейного доступа; три дополнительные restrictive-политики закрывают shortcuts для families/family_members/push_devices. В RPC писем, приглашения, регистрации push и Storage-предикат добавлена такая же проверка, поскольку SECURITY DEFINER обходит RLS. Без них старый APK или прямой запрос мог бы обойти подтверждение.
- Запрещены повторный родитель и несколько членств одного аккаунта. Создание дополнительной семьи старым RPC запрещено. Сын подключается по приглашению; переключатель «Я папа» убран.
- Выход из приложения завершает локальный Auth-сеанс. Смена email владельца и привязка телефонного OTP не предоставляют доступ автоматически.

## Проверки

`npm test`: 62 unit tests и `npm run test:owner-access`. Последний разворачивает baseline и 50 предшествующих миграций в изолированном PGlite PostgreSQL с синтетическими пользователями, затем применяет новую миграцию. 22 сценария проходят: старый сеанс, новый пароль, подмена JWT metadata, RLS, RPC писем/приглашения/push, голосовой Storage, роль папы, приглашение сына, OTP-подтверждение и отзыв сеанса; также четыре существующих SQL-набора безопасности.

PGlite использует минимальные модели Auth/Storage и SHA-256 shim для pgcrypto. Это проверка SQL и правил доступа, а не проверка живого GoTrue, доставки email или полной Supabase-инфраструктуры. Production данные в тесты не копируются. TypeScript проходит.

Мобильный UI 390×844: проверены форма подключения сына и переход папы к входу. На локальном имитаторе Auth проверены переход после пароля на экран подтверждения, запрос одноразовой ссылки с `create_user=false` и точным `papaiya://auth-callback`, а также выход в другой аккаунт. Реальные письма при этой проверке не отправлялись.

Read-only preflight production: один родитель, три существующих неистёкших сеанса, подтверждённый email, отсутствуют дубли ролей и членств. Миграция останавливается, если родитель не единственный; для чистой базы сначала требуется явное создание владельца администратором.
